# Техническое задание — @CHOIR_CLUB_ALA_bot

Версия документа: 1.0 (фаза проектирования).  
Часовой пояс: **Asia/Almaty (UTC+5)**.  
About в BotFather: «Расписание репетиций, отметки, ноты и файлы хора в одном боте 🎶».

---

## 1. Цель

Единый Telegram-бот для хора: расписание репетиций, посещаемость, оплата, поиск нот/транслита/записей. Файлы материалов **не хранятся на сервере** — только идентификаторы Telegram (`file_id`, `file_unique_id`).

---

## 2. Роли и права

### 2.0. Owner (техспец)

- Задаётся в конфигурации: `OWNER_TELEGRAM_ID` (обязательно).
- В БД `role=owner`, **без регистрации**; в интерфейсе и справке «О боте» отображается как **техспец** (`admin.role_badge_owner`).
- Может назначить **одного** дирижёра из активных участников (`member` / `admin`); при смене прежний дирижёр становится `member`.
- Назначает и снимает помощников (`admin`); имеет те же админ- и «дирижёрские» пункты меню, что и дирижёр.
- Операционные уведомления (пропуски, причины, оплата, изгнание) по умолчанию идут **дирижёру в БД**; если дирижёр не назначен — **owner** (`NotificationRecipientResolver`).

### 2.1. Дирижёр (Conductor)

- В БД: одна запись `role=conductor` (назначает owner) **или** legacy: опциональный `CONDUCTOR_TELEGRAM_ID` — при первом действии пользователь становится дирижёром.
- Всё, что могут помощники, **плюс**:
  - получает уведомления об отсутствиях (предупреждения и причины), если назначен;
  - просматривает историю посещаемости по участникам;
  - подтверждает оплату;
  - назначает и снимает помощников;
  - блокирует и разблокирует участников.

**Owner** имеет те же права на модерацию, блокировки, историю и оплату, но уведомления при наличии дирижёра уходят дирижёру.

### 2.2. Помощники (роль `admin` в БД)

- Назначаются дирижёром или техспецом (роль `admin`; в UI — «помощник»).
- Управление расписанием репетиций.
- Загрузка и ведение базы материалов (в админ-чате).

### 2.3. Участники (Members)

- Просмотр расписания.
- Отметка на репетиции (check-in).
- Предупреждение об отсутствии.
- Отметка «я оплатил(а)».
- Поиск песен и материалов по своей/любой партии.

### 2.4. Состояния пользователя

| Состояние | Доступ к функциям бота |
|-----------|-------------------------|
| **pending** | Только сообщение «заявка на рассмотрении» |
| **blocked** | Функции недоступны (история посещаемости сохраняется) |
| **active** | Полный доступ по роли |

## 3. Регистрация

1. Команда `/start`.
2. Ввод **имени** (отображаемого в хоре).
3. Выбор **партии**: сопрано 1, сопрано 2, альт 1, альт 2, тенор, баритон, бас.
4. Статус → **pending**.
5. В **админ-чат** (если привязан) — сообщение с кнопками **Принять** / **Отклонить**; модерация в чате: owner, conductor или `admin`.
6. При принятии → **active**; при отклонении — остаётся pending или отдельная логика отказа (уточняется в сценариях).

Блокировка не удаляет историю; разблокировка возможна (сброс счётчика подряд идущих пропусков). Все действия пишутся в `block_events` (кто, кого, когда, `manual` или `auto`).

---

## 4. Расписание репетиций

### 4.1. Шаблон

- По умолчанию **2 репетиции в неделю**: среда **19:30–21:30**, суббота **16:00–18:00**, адрес **комьюнити-центр** (шаблоны `schedule_templates`, правка в админке).
- Экземпляры репетиций **генерируются заранее** на **4 недели** вперёд (настройка `schedule_generation_weeks` в `bot_settings`, см. `docs/database.md`).

### 4.2. Действия админов

- Перенос конкретной репетиции (дата/время).
- Смена адреса (для экземпляра или шаблона — см. сценарии).
- Отмена репетиции.
- Добавление **внеплановой** репетиции.

### 4.3. Уведомление об изменениях

При **любом** изменении расписания все **активные** участники сразу получают сообщение с текстом из `texts/ru.json` и кнопкой **«Расписание»**.

### 4.4. Просмотр

Участники: кнопка **«Расписание»** — список предстоящих репетиций.

---

## 5. Напоминание накануне (12:00)

- **Когда:** в **12:00** календарного дня **перед** датой репетиции (Asia/Almaty).
- **Кому:** активным участникам.
- **Содержание:** дата, время, адрес репетиции; кнопки **«Да»** / **«Нет»** («Будешь?»).
- **«Нет»:** бот просит причину. С **текстом** → уважительное предупреждение (`warned`), причина дирижёру. Кнопка **«Нет причины»** → **неуважительный** пропуск (`unexcused`), счётчик дисциплины.

---

## 6. Check-in на репетиции

- **Когда:** в **момент начала** репетиции (по расписанию экземпляра).
- **Кому:** участникам, которые **не** предупредили об отсутствии заранее.
- **Вопрос:** «Ты на репетиции?» — **Да** / **Нет**.
- Ответ принимается **до конца** репетиции (время окончания задаётся в экземпляре или вычисляется по длительности по умолчанию).
- **Нет ответа до конца** → **неуважительное отсутствие** (unexcused).
- Админ может **вручную исправить** отметку.

---

## 7. Предупреждение об отсутствии заранее

- До **начала** репетиции:
  - **«Не приду»** → выбор репетиции → **обязательная** причина; без текста отметка не ставится.
  - **«Нет»** накануне или в check-in → причина **опциональна**; **«Нет причины»** = неуважительный пропуск.
- С **причиной** → `warned` (уважительно), сброс счётчика неуважительных пропусков.

---

## 8. Серия неуважительных пропусков

- Считаются **подряд** только отметки **unexcused** без intervening attendance или advance warning.
- **3-й подряд:** участнику сообщение о «3 пропусках» и одной оставшейся попытке.
- **4-й подряд:** участнику сообщение об «изгнании»; дирижёру уведомление с именем участника (автоблокировка — см. сценарии и БД).
- Сброс счётчика: любая **явка** или **предупреждение заранее**.

---

## 9. История посещаемости

- Дирижёр выбирает участника → по каждой репетиции: **был / предупредил / неуважительно**.
- Сводка **за месяц** по всем участникам.

---

## 10. Оплата

### 10.1. Напоминание 23-го в 12:00

- Участникам напоминание об оплате **следующего** календарного месяца (например, 23 октября — за ноябрь).
- Текст: `bot_settings.payment_reminder_1_text` или стандарт из `texts/ru.json` (плейсхолдер `{month}`).
- **Не отправлять**, если оплата за целевой месяц уже **подтверждена** дирижёром.
- Кнопка **«Я оплатил(а)»** → отметка участника; дирижёр получает уведомление с **«Подтвердить»**.

### 10.2. Подтверждение дирижёром

- Дирижёр может подтвердить оплату **любого** участника, даже без отметки участника.

### 10.3. Напоминание 1-го в 12:00

| Состояние | Действие |
|-----------|----------|
| Подтверждено дирижёром | Ничего не отправлять |
| Есть отметка участника, нет подтверждения | Сообщение о «несовпадении показаний» |
| Нет отметок | второе напоминание (`payment_reminder_2_text` / `payment.reminder_second`) |

### 10.4. Интерфейс дирижёра и техспеца

Список за месяц: **подтверждено** / **ждёт подтверждения** / **не оплачено**. Inline **«Тексты напоминаний»** — правка обоих текстов, сброс к стандартным.

Дни и час — `bot_settings` (`payment_reminder_day_1`, `payment_reminder_day_2`, `payment_reminder_hour`). В `.env.example` они указаны как справка; в рантайме читаются из БД.

## 11. Песни и материалы

### 11.1. Хранение

- На сервере **нет** бинарных файлов — только `file_id`, `file_unique_id`, метаданные.

### 11.2. Загрузка (админ-чат)

- Приватная группа: основной id в `bot_settings.admin_chat_id` (техспец меняет кнопкой **«Админ-чат»**); fallback — `ADMIN_CHAT_ID` в `.env`. Бот — **администратор** чата.
- Для кнопки «Открыть админ-чат»: супергруппа `-100…` даёт ссылку `t.me/c/…`; иначе — `ADMIN_CHAT_LINK` в `.env`.
- Админ отправляет файл:
  - **С подписью:** формат «Название песни, партия» → тип определяется контекстом или уточняется (см. сценарии).
  - **Без подписи:** бот спрашивает кнопками: песня (или создать новую), тип (ноты / транслит / запись), для записи — **несколько партий** (кнопка **«Готово»**).

### 11.3. Дубликаты

Если `file_unique_id` уже есть — карточка «уже загружен» (песня, тип, партия, кто, когда), **без** повторной записи.

### 11.4. Версии

- **Ноты и транслит:** одна **текущая** версия на песню; при новой загрузке — вопрос «Заменить старые ноты?»; старая уходит в **архив** (виден админам, можно восстановить).
- **Записи:** по умолчанию **добавляются** к существующим для партии; админ может список → заменить или удалить конкретную.

### 11.5. Участники

- Только **актуальные** материалы (не архив).
- **«Найти песню»** → ввод названия (без учёта регистра, частичное совпадение) → список → карточка: **Ноты**, **Транслит**, **Записи партий** → выбор партии → отправка всех записей для партии.
- **«Мои записи»** — shortcut на записи своей партии.

## 12. Нефункциональные требования

- Webhook + HTTPS на shared hosting; секрет webhook в конфиге.
- Cron для задач по расписанию (см. `docs/scenarios.md`).
- Идемпотентность рассылок: каждая задача фиксирует, что уже отправлено (таблица `job_deliveries`).
- Локализация: русский (`texts/ru.json`).
- Совместимость схемы БД: MySQL (prod) и SQLite (локальная разработка).

## 13. Реализация

- **Стек:** PHP 8.2+, Nutgram 4.x, Composer, PDO (MySQL на [alabot.liveband.kz](https://alabot.liveband.kz), SQLite локально).
- **Деплой:** shared hosting без SSH — см. [README.md](../README.md); после обновления — `public/admin/migrate.php`, cron.
- **Тесты:** `composer test` = PSR-4 check + PHPStan level 2 + PHPUnit.
- **Код:** handlers, jobs, миграции в репозитории; сценарии — [scenarios.md](scenarios.md).
